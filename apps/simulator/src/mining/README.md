# D01 mining simulator layer

This mining-scoped package is independent of the simulator's existing triathlon
models, generators, Eventstream publisher, and `DEMO_PROFILE`. The repository
root entry point does not re-export mining types. After building the simulator,
import its public API and types from `@triathlon-twin/simulator/mining` (backed
by `dist/mining/index.js` and `dist/mining/index.d.ts`). The existing
`@triathlon-twin/simulator` entry point remains unchanged. Nothing here starts
a hosted run or publishes to Fabric.

`plant-catalog.json` is the byte-for-byte published D01 metadata asset. Its
SHA-256 and the individually verified authored-asset receipts are recorded in
`catalog-receipt.json`; the metadata preserves the authored module dimensions,
equipment/tag joins, directed stream ports, and the original strict v1 schema.
The catalog is fictional authored parametric geometry and demo assumptions, not
surveyed engineering truth. Its source project is MIT-licensed; see `LICENSE`.
The receipt pins remote GLBs and layout for later UI use without importing the
GPU reconstruction toolchain or copying those assets here.

The pinned functional specification describes the raw catalog tag field
`suggested_interval_ms: 1000` as an initial placeholder, not the publication
cadence; it must not drive validation or one-second publishing. Export
`toD01PublishProfileRecords()` from `@triathlon-twin/simulator/mining` for the
operational profile. Each row has `plant_id`, the raw `catalog_version`,
`profile_version` (`d01-publish-profile-v1`), `tag_id`, and `interval_seconds`
(30 or 60). Join by plant, catalog version, profile version and tag ID.
This profile covers all 56 tags (45 at 30 seconds and 11 at 60 seconds);
`getD01TagIntervalSeconds` uses the same mapping for simulator output and numeric
validation. The original `record_json` and catalog hash remain unchanged. The
profile follows `docs/diamond-plant-demo.md` at the revision in the receipt.

The v2 numeric and state payload schemas are separate files. The flattened
transport body adds `entityType` (`PlantTelemetry` or `PlantStateEvent`) outside
those strict payloads. `simulator.ts` exposes deterministic 5-second stepping;
callers supply each UTC tick, so offline tests can step without sleeping while
no future or hosted timestamps are generated by a live publisher.
The numeric `quality` enum preserves the pinned v1 values `good`, `uncertain`,
and `bad`; this simulator emits only `good`. Consumers should retain uncertain
and bad observations as structurally valid but exclude them from calculations
that require good-quality samples.

The simulator accumulates one transport batch every 30 simulated seconds
(flushing a final partial batch if a custom duration ends between boundaries).
An unacknowledged batch blocks further steps; retry it with `getPendingBatch()`
and acknowledge its `batch_id` only after successful delivery. This preserves
event IDs and prevents accidental overlapping sends. `events` contains only
numeric and state transport bodies. `alert_transitions` contains **non-authoritative
simulator diagnostics**, not operational incidents or a third `entityType`;
they must not be published as actual incidents. The private evaluator has four
simplified threshold/gap rules, not the required five-rule incident engine: it
does not implement escalation, hold timers, startup gating, state-heartbeat
freshness, or acknowledgment workflows. Its measurements and telemetry gaps
are not scripted scenario labels, but that does not make the evaluator suitable
for real observations. Scenario oracles should remain separate from observed data.
